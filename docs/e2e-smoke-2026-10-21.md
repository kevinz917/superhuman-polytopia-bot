# End-to-end throughput smoke of main 7f66add (Stage A + Rust engine), 2026-10-21

**Result:** with the Rust engine and Stage A together, training runs at **41k samples/s steady (39k over the whole
20 min) vs c5's 26.9k, i.e. 1.5× faster**. It does that with **half the actor fleet** (6 containers instead of 12), so
it costs **~$0.08–0.10 per million samples vs c5's $0.225 (2.3–2.7× cheaper)**. The wall is still the learner's
host-side batch assembly: 4.3 s per update vs 1.5 s of GPU training. Rust made the actors cheaper but did not raise
the ceiling. The full-fleet Rust actor container ran clean: 0 errors, 0 restarts, 0 reconnects, no orchestrator
replay.

Caveat: c5 trained 3 epochs per batch and this smoke trained 1 (the Stage A recommendation; stage-a-e1 matched c5's
record vs c3 per sample through 79M samples and was 3–4 points under at 96M). So the speedup is in samples per second,
not yet in strength per hour.

Ledger `runs/e2e-smoke/budget.json` (copy in `docs/e2e-smoke/`): **$5.92 billed** of the $15 cap ($4.54 smoke, $0.69
failed 4×L4 smoke, $0.69 benches).

- No crashes or mismatches: 0 errors, 0 restarts, 0 reconnects. All processes exited with SIGTERM (-15) at the
  learner's stop, which is the normal shutdown path. The 12-container 4×L4 attempt also had all 192 processes connect
  and stream (1.26M samples in ~100 s, 0 errors) before its learner died.
- Two of the six containers ran ~25% slower (357–379 vs 464–470 steps/s per process). That looks like host-CPU
  variation between Modal machines, not a code path, and is worth knowing when sizing a fleet.
- Per process 360–470 steps/s here vs ~525 in the unloaded actor bench: the actors were partly throttled while the
  inbox was full during warm-up.
- **Fleet sizing: 6 containers is about right for this learner.** At ~6.5–7k samples/s per container, 6 containers
  supply ~39–42k, which matches the ~42k the learner can absorb. c5 used 12. Until A6 lifts the assembly ceiling, more
  containers would only fill the inbox; after A6, each extra ~7k samples/s costs one more container (~$1.2/h billed).

- Hourly: ~$12.4/h billed for 1×H100 + 6 actor containers (launcher estimate $10.90/h; Modal billed ~1.14× that here,
  vs 1.31× for c5) vs c5's $21.7/h.
- Per sample: $4.54 / 47.2M = **$0.096/M** for the whole 20-min run including startup and compile; ~$0.084/M at the
  steady 41k. c5: $130.46 / 580M = **$0.225/M**.
- In the hourly bill the H100 is ~$4 and the actors most of the rest, so halving the fleet saved more than any GPU
  change could.

## Learner GPU: L4 vs H100 (the user's L4 default)

`bench_learner`, c5-omni recipe, epochs 1, training precision; steady epochs (the first includes 31–49 s of compile):

| GPU | $/h | batch / minibatch | result | GPU samples/s |
|---|---|---|---|---|
| 1×H100 80 GB | 3.95 | 262,144 / 16,384 | 1.62 s/epoch + 1.0 s upload | 161k |
| 1×L4 24 GB | 0.80 | 262,144 / 16,384, 8,192, 4,096 | out of memory | — |
| 1×L4 | 0.80 | 131,072 / 4,096 (changed recipe) | 10.56 s/epoch | 12.4k |
| 1×L40S 48 GB | 1.95 | 262,144 / 16,384 | out of memory | — |
| **4×L4** | 3.20 | 262,144 / 16,384 (c5 recipe, 4,096 per GPU) | 5.42 s/epoch + 0.5 s upload | **48k** |
| 8×L4 | 6.40 | 262,144 / 16,384 | 2.63 s/epoch + 0.3 s upload | 99.7k |

- A single L4 can't run the recipe: the per-minibatch activations (policy, reference, anchor and the omniscient critic
  all run the conv stack on every row, no rematerialisation) need 16 GiB at minibatch 16,384. Where it fits, it is
  13× slower per sample than an H100.
- **4×L4 fits the exact recipe in the bench and trains at 48k samples/s**, which is above today's ~42k assembly
  ceiling, for $3.20/h vs $3.95. But the real 4×L4 run (`e2e-l4x4-smoke`) ran out of memory at update 1 (9.34 GiB in
  `jit_epoch`). The bench leaves out the assembler thread, which scores the next batch on the same cards while one
  trains: the padded view upload plus the value pass, plus a gathered copy.
- To make 4×L4 work: gradient accumulation inside the epoch (split each per-GPU minibatch into 2–4 microbatches and
  average their gradients before one Adam step). Every loss term is a per-row mean (`ppo.loss`, critic MSE; unit_*
  terms are off), and the network uses layer norm, not batch norm, so the update is the same up to float summation
  order. Optionally also drop the old device batch before uploading the next. Expected saving vs H100: ~$0.75/h of a
  ~$12/h arm (~6%).

## Code change in this branch

`experiments/modal_distributed_rl.py`: `GPU_RATE['L4'] = 0.80` (`launch --gpu L4[:n]` no longer raises KeyError), and
`learner_bench` reads an `env` dict from the config (e.g. `POLYTOPIA_HEAD_PRECISION`), as `launch --learner-env-json`
does for the learner.

## Follow-ups

1. A6 host assembly (shared-memory workers, pinned buffers, value-pass upload off the critical path): the only lever
   that raises samples/s now; the GPU is idle 74% of the time.
2. Gradient accumulation knob so 4×L4 can replace the H100 learner (small saving, matches the L4 default).
3. A strength-per-hour check of 1 epoch vs c5's 3 epochs over a longer run, since this smoke measures speed only.
