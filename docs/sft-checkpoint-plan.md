# Research plan through the first Qwen3-4B SFT checkpoint

**Execution update (2026-10-16):** SFT-0 work has started. See the [execution log](sft-execution.md) for the live adapter, public memory, reserved maps, qualification attempts and model profiling. No trained game checkpoint is claimed.

**Status:** proposed protocol, 2026-10-16. No demonstration corpus, trained adapter, or validated checkpoint is claimed here. This document specifies the work from a complete simulator to the first supervised fine-tuning (SFT) result. The broader [experiment plan](experiment-plan.md) covers later reinforcement learning (RL) and transfer experiments; the [environment contract](environment-contract.md) defines the policy interface.

## Question and checkpoint

Can a 4B instruct model learn from a competent, observation-limited scripted Polytopia player and then finish full games on unseen maps while choosing legal, useful actions? The deliverable is **SFT-0**: a versioned Qwen3-4B adapter, its data and evaluation receipts, and a clear pass/fail decision. This is an engineering and learning checkpoint, not evidence that Polytopia training transfers to other tasks. Preserve the unchanged model and the evaluation protocol so that a later transfer study can compare them fairly.

Use [Qwen/Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507), the non-thinking instruct checkpoint. The initial pinned Hub revision is `cdbee75f17c01a7cc42f958dc650907174af0554`; record the exact model, tokenizer, chat template, and file hashes when weights are fetched. The model's license and intended chat format are in its [model card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507). SFT-0 trains an action-only LoRA adapter on the original model. It does not train a value model or choose between PPO and GRPO; those decisions require actual rollout and reward evidence after this checkpoint.

The target setting is two-player Bardur versus Bardur, 14×14 Drylands with fog, native elimination victory, and all mechanics reachable on generated maps. An 11×11 setting is useful for integration and debugging, but cannot substitute for the target evaluation. Fix the exact native rules profile and map generator in the experiment manifest. A map labeled Drylands is not assumed to contain only land; inspect generated maps and cover any reachable water mechanics. Each model call selects one atomic legal action, so long games contain many calls, including multiple actions within the same turn.

## Prerequisites before collecting labels

1. **Finish the playable environment.** Require `FULL_GAME_READY=True` under a documented native rules profile, complete legal actions, fog, all reachable city, economy, research, combat, diplomacy, exploration, movement, capture, naval, end-turn, and terminal behavior, procedural reset, deterministic per-game RNG, and no capacity overflow or host fallback for game logic. The simulator's current transition tests do not meet this gate. The pinned Polyfish profile remains a differential-test oracle; approved departures in [native-rules-exceptions.md](native-rules-exceptions.md) require independent regression tests. Compare at least 100 complete seeded traces action by action wherever the reference applies, and test native exceptions separately. Never accept an untested discrepancy as a teaching signal.
2. **Prove observation integrity.** The teacher, model prompt, and legal-action list must derive only from what the acting player could know. Test pairs of states with the same observable history but different hidden enemy state: the serialized prompt, memory, and action catalog must agree whenever the game itself would not reveal a difference. The teacher must not inspect the hidden map, future randomness, enemy resources, or full state to choose its move. Audit public error messages and action ordering for leaks. Keep trusted engine snapshots outside training examples.
3. **Fix the interface contract, then optimize and freeze prompt wording.** Complete the bounded prompt stage below before rendering the SFT corpus or fitting any game adapter. The prompt includes rules, active player, turn, resources, technology, visible map, owned and observed units/cities, last-seen facts with their observation turn, recent public events, and the **complete** legal catalog. It emits exactly one JSON object such as `{"action_id":"a17"}`. IDs belong only to that observation version; store the corresponding semantic command in the dataset. Choices such as city rewards and end-turn are explicit catalog entries. Measure prompt sizes on actual full games. The working target is 2–4K input tokens, with an 8K context allowance and at most 32 generated action tokens. If a state exceeds the limit, revise and version the serialization or expand the context; never silently omit actions.
4. **Freeze evaluation before fitting.** Reserve disjoint map manifests by generator seed and board hash: at least 500 distinct training maps, 200 validation maps, and 500 untouched final-test maps, each with both seat assignments. Generate enough training episodes from training maps to support the sampling plan below. Inspect for duplicate or symmetry-equivalent boards across splits. Hold final-test seeds and outcomes away from teacher tuning, prompt tuning, adapter selection, and retry decisions. Version the native rules, generator, serialization, teacher and opponent code, seeds, and split hashes together. Freeze the unchanged 4B baseline protocol against B-lite using the same prompt and inference budget as SFT-0: run its 25-map smoke pilot before main training, then complete all 200 validation maps with both seats after that cost gate passes. Reuse the 50 pilot baseline games only if every model, prompt, opponent, rule, and decoding setting remains identical.

The game horizon limit is 100 full rounds or 10,000 atomic actions, whichever occurs first. A native victory, loss, or draw is a terminal outcome. A limit hit is a **truncation**, reported separately; it is never converted to a win or ordinary draw. Decide and document the exact native victory condition before collecting labels. Do not start SFT because a narrow fixture suite passes if complete target games still fail.

## Decision context and factual memory for SFT-0

Use **one fresh LLM context per atomic decision**, containing the frozen rules/instructions, current public state, compact factual memory, and complete legal catalog. The model returns only the action JSON. This permits decisions with long-term consequences without carrying a full conversation between moves. Model weights remain fixed during gameplay. Within one decision, the existing bounded invalid-response repair exchanges may remain in context; discard those exchanges after the decision resolves, retaining them in diagnostic logs.

The game runner maintains memory deterministically and separately for each `(episode, player)`. The initial proposal is **the last five executed own actions plus at most 32 historical observation records**, in addition to the current public state. Each action record contains its semantic command, turn and decision revision; it is a record of what happened, not a model-written explanation. Historical records contain only previously observed facts that are useful and absent from current public information, with `last_seen_turn` and observation revision. Examples include a last-seen enemy position when the environment's visibility rules make it unavailable now. Such records remain explicitly historical and uncertain; never present a remembered unit as currently present or infer its unseen movements.

Current observations take precedence over remembered facts. Reobserving an entity/location updates or invalidates its old record only to the extent justified by the new public observation. Do not consult live hidden state to refresh or remove memories. At the historical-record cap, retain the most recently observed records with a stable public-key tie-break; preserve the full public observation log outside the prompt. Do not duplicate terrain or other facts already exposed in the current state. The complete current observation and legal catalog are never pruned to make room for memory. Measure the proposed caps on development games, then freeze the schema, retention rules and token allocation before prompt optimization and corpus rendering. Context overflow remains an explicit error, requiring a versioned representation/budget change.

No model-written strategic notebook, generated summaries, persistent plan, or learned memory writer is part of SFT-0. If failure analysis later shows repeated objective switching or abandoned investments despite adequate factual context, test persistent strategic intent as a separate controlled experiment with its own output schema and supervision. Action-only SFT does not train a plan-writing channel.

Use the **same memory builder and public information contract** for the scripted teacher, demonstration generation, base-model evaluation and SFT gameplay. The teacher may use these public remembered facts; it may not access an additional private history. Store the exact memory supplied at each decision, its schema/builder revision, and an input digest. Reconstruct saved-position inputs from observations available up to that decision only, including for off-trajectory teacher relabeling; later outcomes or future observations must not enter memory.

Before real collection, validate seat isolation, clearing on a new episode, deterministic replay/restore of memory, idempotent repeated observation reads, timestamp ordering, stale-fact replacement, record-cap behavior, and identical memory for identical public histories under different hidden worlds. Snapshot/restore of an evaluation episode must restore both the engine and the corresponding public memory history. Prompt-search candidates share the same frozen memory policy; the optimizer cannot expand information access or write memory itself.

**Implementation status:** the current schema supports timestamped remembered tile facts, but the engine-connected memory builder, recent-action history, and richer historical entity records still require implementation and a schema revision. The current heuristic teacher uses current observations. These are required integration tasks before teacher qualification and prompt optimization, not capabilities established by the existing fixture tests.

## Starting-prompt optimization before SFT

Run a bounded **GEPA-style prompt search** on the unchanged pinned 4B instruct model after the environment, public observation boundary, and scripted evaluation opponents are usable, and before the game-SFT smoke run. [GEPA](https://github.com/gepa-ai/gepa) provides reflective prompt evolution using execution traces; applying it to this game is our proposed experiment, not an established Polytopia result. The optimizer is not implemented or run yet. Local synthetic plumbing checks can proceed before this stage.

A stronger reflection model reads the current prompt, public observations, model actions, parser errors, and outcome summaries from prompt-development runs, then proposes targeted edits. The 4B model makes every gameplay decision with frozen weights. The reflector does not supply per-position actions during evaluation. Keep hidden snapshots, final-test maps, and private opponent facts out of reflection inputs; candidates must not contain instance-specific answers or map identifiers.

Allow changes to explanations, organization, and general strategic guidance. Keep authoritative mechanics, available public information, complete legal catalog, semantic action meanings, JSON response contract, retry policy, decoding, and context/output limits fixed. Human-readable descriptions must use the same trusted public facts for every candidate; they cannot invent costs or consequences. Reject candidates that contradict mechanics, hide actions, require additional tools, or exceed the registered token budget. Cap instruction length before search. Any serializer or information-content change is a separate versioned interface experiment and invalidates comparisons to the previous interface.

Reserve a prompt-development map pool disjoint from corpus training maps, SFT validation maps, and final game-test maps; check exact and symmetry-equivalent board overlap. Use 10 search maps and 10 additional confirmation maps, with both seats. Draw the 100 saved development positions from search-map traces, covering economy, exploration, combat, capture, mandatory choices, and end-turn decisions. Use verified unambiguous decisions for correctness checks; agreement with the heuristic teacher is diagnostic, not an optimal-action label.

| Stage | Initial bounded allocation | Decision |
| --- | --- | --- |
| Propose and screen | Generate six revised prompts; evaluate those six plus the original on the same 100 saved positions: **700 first-attempt decisions**, with at most two logged repairs each. | Reject format, legality, context, and clear comprehension failures. Select two revised candidates using the recorded screening criteria. If fewer than two survive, do not silently expand the search. |
| Gameplay selection | Original plus the two surviving revisions × 10 search maps × both seats × one frozen opponent: **60 full games** at most. | Prefer higher paired win-equivalent score, subject to completion and validity checks; retain the original when gains are unclear. Teacher agreement and the reflector's opinions cannot choose the gameplay winner. |
| Confirmation | Provisional winner plus original × 10 fresh confirmation maps × both seats × a second frozen opponent: **40 full games** at most. | Check whether the apparent benefit persists. Report map-paired uncertainty and failures; this sample is a sanity check, not strong statistical evidence. If confirmation is inconclusive or negative, retain the original for the first SFT experiment. |

Freeze opponent versions, position/map IDs, acceptance and tie-breaking rules, and generation settings before scoring candidates. Do not iterate on the confirmation set: any later search needs fresh confirmation maps. The default allocation is **one search batch, at most 100 full games plus the saved-position screen**. Set a dollar and occupied-GPU-hour ceiling from measured inference throughput before launch, including any profiling runs, reflector API usage, repairs, and failed games. Stop at that ceiling; do not automatically add rounds. Prompt-search costs are additional to the existing SFT/game-evaluation table. Prompt-development games do not count toward the main validation or final-test sample sizes.

Freeze and hash the chosen prompt, renderer, rule glossary, tokenizer/chat template, and budgets **before rendering the smoke/main demonstrations and before any game-SFT optimizer step**. Use that exact interface for the unchanged-model baseline and both SFT seeds. Raw semantic teacher traces may be collected earlier, but must be rendered again under the final prompt. Re-run token-length and response-mask audits after freezing. Any later prompt change requires re-rendering the corpus and rerunning affected baseline/training comparisons; never silently give SFT a better prompt than the base.

Retain every candidate, its parent and edit rationale, reflection-model revision/settings, development manifests, traces, screening/game scores, costs, and the final selection receipt. Record no improvement honestly. This stage improves the starting gameplay interface; APEX setup remains deferred until after SFT and provides no prompt-search feedback.

## Scripted teacher and demonstrations

Build one deterministic **T-main** policy against the public observation and complete legal catalog. It should have explicit, inspectable priorities for survival, city income, expansion, technology, unit placement, combat trades, capture, and end-turn. Resolve tied actions from a stable hash of the public input and teacher version. It may use hand-coded heuristics or bounded search over **observable** state, but it cannot call a privileged simulator branch with hidden information. A replayable trace should show the observation, each legal semantic command, the chosen command, the priority or score used, and the resulting state. This makes a bad label debuggable.

Create at least two distinct scripted opponents for state diversity: an economy/expansion policy and a combat/pressure policy, plus a weak legal-action baseline. The opponents need not be good teachers. T-main supplies the action labels in all SFT examples, including positions reached against different opponents and positions where T-main is losing. Keep complete losing and truncated episodes; filtering to wins alone would hide recovery decisions and bias the state distribution. Search-generated labels, human replays, and model-written rationales are optional later studies, not dependencies for SFT-0.

Qualify T-main before freezing it: zero illegal actions in 10,000 attempted decisions, at least 95% native game completion over 200 validation-map games, less than 5% truncation, and a predeclared positive margin over the weak baseline with paired maps and swapped seats. A proposed practical target is at least 60% win-equivalent score against that weak baseline; if no available baseline offers a meaningful headroom range, establish a weaker frozen opponent using validation maps **before** final testing. Report performance against the economy and combat opponents as a robustness check. These thresholds establish usable demonstrations, not expert play. Any teacher edit creates a new version and requires repeating qualification.

Collect full episodes on training maps, then select **5,000–10,000 examples for a pipeline smoke run** and **50,000 unique examples for the main corpus**. An example is one observation, full legal catalog, and T-main's selected semantic action rendered as the response-local ID. Keep episode linkage, map/seat/opponent/rules versions, decision index, phase, action family, result, and why a position was retained. Deduplicate within and across episodes by a hash of the public observation/history and semantic catalog; if identical inputs have conflicting teacher actions, investigate before training. Report retained and rejected counts. Cap overrepresented trivial end-turn choices by sampling, while retaining complete source trajectories and rare forced choices. Stratify the 50,000 by opening, economy, exploration, combat, and late game; report actual counts and deliberately include all reachable action families. Inspect at least 100 random labels plus examples from each rare family by replaying the chosen action against the frozen environment.

After the smoke run, roll that candidate on **training maps only** and collect up to 10,000 additional public states where it goes off the teacher's trajectory. Ask the frozen T-main to label those states, using only its public input. These relabels can replace at most 20% of the 50,000 main examples; keep the source tag and report whether the extra collection was needed. This is one planned distribution-repair pass, not RL: there is no reward gradient, policy update from outcomes, or extra hidden-state access. Restart the main run from the pinned base adapter initialization; the smoke model is a diagnostic, not silently continued training.

Export the exact chat messages and expected completion for every example. Apply the pinned Qwen chat template once; train loss on the assistant's JSON action and end-of-message token only. Mask the system and user text, legal catalog, padding, and any later turns. Verify the mask on at least 64 hand-inspected examples, including long catalogs and mandatory choices; reject any sample whose catalog exceeds the registered context limit. If the template or trainer cannot prove this mask, stop and fix that before fitting. This follows the prompt/completion and completion-only controls in the [TRL SFT trainer documentation](https://huggingface.co/docs/trl/sft_trainer); set Qwen's `<|im_end|>` end-of-message token explicitly rather than assuming a default EOS. Confirm the final target ID refers to the selected semantic command after catalog shuffling.

## SFT implementation and staged runs

Use the separately pinned runtime in `training/pyproject.toml` and `training/uv.lock`: Transformers Trainer, PEFT, PyTorch, and tokenizer libraries, with the resolved versions and CUDA stack in each run receipt. The implemented runner passes explicitly audited response-only labels directly to Trainer instead of delegating templating/masking to TRL; the SFT objective is unchanged. See [SFT pipeline](sft-pipeline.md) for commands and validation evidence. The simulator's JAX package is a separate dependency set. [PEFT LoRA](https://huggingface.co/docs/peft/developer_guides/lora) supplies the adapter mechanism. The primary recipe is BF16 base weights, frozen embeddings and language head, LoRA rank 32, alpha 64, dropout 0 on `q_proj`, `k_proj`, `v_proj`, `o_proj`, `gate_proj`, `up_proj`, and `down_proj`. Use AdamW, learning rate `1e-4`, 3% warmup followed by cosine decay, max gradient norm 1, and an effective batch of 64 examples. Select microbatch size 1–4 and gradient accumulation by a memory profile; log the actual effective batch. Train for one epoch, with no sequence packing, and save at 25%, 50%, and 100% of steps. For each seed, choose the snapshot with the highest conservative win-equivalent score against B-lite on the 200 validation maps with both seats; break ties by fewer first-attempt errors and then the earlier snapshot. Run two independent main training seeds from the identical base and corpus.

The training path has explicit diagnostics:

| Stage | Work | Must be true before proceeding |
| --- | --- | --- |
| Starting prompt | Run the bounded development-only search above and freeze the selected prompt. | A selection receipt exists, budgets are recorded, and base/SFT will share the same interface. |
| Data and template | Render 64 hand-inspected examples; replay actions and inspect target masks. | Every target is legal, JSON is parseable, only response tokens receive loss, and hidden information is absent. |
| Fit sanity | Overfit a separate 128-example training subset; check gradients and checkpoint reload. | Adapter parameters change, base parameters do not, loss stays finite, and training-set target accuracy rises sharply. This is a plumbing check only. |
| Smoke and cost gate | Train on 5,000–10,000 examples; run the saved-position check and 100-game pilot below, then gather off-trajectory states if needed. | The model shows observable action learning and some complete games, and measured calls/game, throughput, and cost justify the main run. |
| Main | Train two seeds on the frozen 50,000-example corpus; choose the step for each seed using validation only. | Both adapters and full run receipts exist; any failed seed is reported rather than hidden. |
| Final | Evaluate the chosen step from each seed and the unchanged base on the untouched test manifest. | Apply the acceptance rules below once; publish all outcomes and uncertainties. |

**Two different kinds of validation drive cost.** A saved-position check presents a frozen observation to the model once and checks its JSON, legality, and agreement with T-main. It never advances a game. Live-game evaluation repeatedly asks the model for an action, applies it in the simulator, and asks again after the next observation; retries add calls. The two main SFT runs read 50,000 examples each, or 100,000 training examples in total. By contrast, the full game protocol below could require 5.28 million inference calls at the illustrative 600 decisions/game, about 53 times as many examples/calls. Training includes backward passes and is more expensive per example, so this comparison explains workload scale rather than predicting GPU time.

Before spending on the main 50,000-example runs, evaluate the unchanged base and the smoke adapter on the same 5,000 teacher-labeled **validation-map positions** (10,000 independent inference calls total). Then play each model on 25 validation maps with both seats against B-lite: **100 live games total**. A passing diagnostic has the smoke model at least 95% first-attempt valid on saved positions, at least 5 percentage points more semantic agreement with T-main than the base, at least 80% native completion in its 50 games, and no reproducible observation leak or rule failure. These are inexpensive continuation criteria, not final performance claims. If they fail, diagnose the prompt, labels, trainer, or simulator before the main runs; keep final-test maps sealed. Record calls/game, prompt tokens/call, retries, occupied GPU time, and dollars/game from this pilot. Use those measurements to project the full protocol and set a spend limit before starting it. If the measured cost exceeds the available budget, report the final gate as unevaluated rather than silently reducing its sample or claiming a pass from the pilot.

The loss scale is small relative to prompt processing. At 50,000 examples, 2,048 input tokens plus 32 completion tokens imply about **104 million processed tokens per epoch** and about **782 optimizer steps** at effective batch 64; two seed runs double the processed tokens. If actual prompts approach 4,096 tokens, that estimate is about 206 million per epoch. Only the completion contributes to supervised loss, but the whole prompt consumes compute and memory. The corpus and cost ledger must use measured token counts, not these planning averages.

Profile the complete data path and 128-example fit before reserving the main runs. A single 48–80 GB GPU with BF16 LoRA is the first configuration to test; a 24 GB GPU with 4-bit QLoRA is a separately labeled fallback whose behavior and cost may differ. Check a compatible multi-GPU arrangement only if profiling requires it. Set an **initial planning ceiling**, not a promised duration, of 4 GPU-hours for profiling and 8 GPU-hours for each main seed (20 GPU-hours total); report compilation, data preparation, training, checkpointing, and failed attempts separately. If measured throughput cannot meet that ceiling, re-estimate before running; never shrink the validation silently. Game evaluation can dominate training: at an illustrative 600 model decisions per game, 6,000 evaluated games with 2,080 tokens per decision imply roughly 7.5 billion processed inference tokens, before retries. Measure actual decisions, prompt lengths, GPU throughput, and dollars per game on validation maps, then budget the final test accordingly. The 6,000 games correspond to three model versions (base plus two SFT seeds), two frozen opponents, 500 maps, and two seats.

## Evaluation and acceptance decision

Use one frozen prompt format and the same model-call budget for the unchanged base and both SFT seeds. Primary decoding is deterministic greedy generation, maximum 32 new tokens, with no legal-token constraint. Parse exactly one JSON object and reject extra text, unknown IDs, stale IDs, and illegal commands. On an invalid response, return the same public observation plus a versioned public error; allow at most two retries, then record an agent forfeit. Count every attempt, including retries and malformed output, in legality and cost. Never substitute a scripted move after failure. A separately labeled constrained-decoding diagnostic is allowed, but cannot replace this primary result. Shuffle catalog order with recorded, public-state-independent RNG in a sensitivity test; test that semantic choices remain consistent when only response-local IDs change.

Before fitting, freeze two final opponents: **B-lite**, a weak but nontrivial legal bot with enough headroom to distinguish base from SFT, and **B-counter**, a different economy/combat style not used as a demonstration labeler. The primary gameplay comparison is SFT-0 versus the unchanged base against B-lite. Use the same 500 final-test maps and both seat assignments for each model/opponent pair. Separately, reserve at least 5,000 teacher-labeled public decisions from final-test maps for semantic action agreement; these never enter SFT or checkpoint selection, and agreement is diagnostic rather than proof of game skill. Use a separate validation-map sample for checkpoint selection. Also report performance against T-main and the other scripted variants on validation maps. Include the scripted teacher's final-test result for context, but do not tune to it. Complete all validation choices before exposing final-test results.

Define win-equivalent score as `1` for a native win, `0.5` for a native draw, and `0` for a native loss or agent forfeit. A limit truncation is **unresolved** and reported separately; for the primary conservative score, assign it `0`, plus a sensitivity interval that assigns all truncations `0.5` or `1`. Never label a truncation as a native draw. Compare models on paired map/seat blocks, with confidence intervals from a map-cluster bootstrap (10,000 resamples). Report per-seat and per-opponent outcomes, completion and truncation rates, calls/game, invalid first attempts, retries, prompt-length distribution, action families, and failure traces. Show both SFT seeds; a single selected seed does not establish repeatability.

Classify **both main seeds** with two separate decisions. A **usable SFT warm start** requires all readiness gates below. **SFT-only gameplay gain** additionally requires the gameplay gate. This distinction matters because [Odysseus](https://arxiv.org/html/2605.00347v1) reported that its lightweight SFT alone did not improve game progress, although it improved later RL. Our action-labeled SFT may behave differently, so report what actually happens here.

| Gate | Acceptance rule |
| --- | --- |
| First-attempt format and legality | At least 99.9% of all model decisions produce a parseable, currently legal action on the first attempt, with at least 10,000 observed decisions per seed; report a map-cluster confidence interval. |
| Full-game reliability | At least 95% of games reach a native terminal; fewer than 5% hit the research horizon. Forfeits are separately counted as failures, not native completions. |
| Teacher learning | On the frozen 5,000-position final-test sample, semantic agreement with T-main exceeds the unchanged base by at least 10 percentage points, with a positive lower 95% map-cluster confidence bound. Report agreement by action family. |
| Robustness | Report B-counter and T-main results, phase/action-family breakdowns, and action-order sensitivity; no systematic catalog or fog leak may explain the gain. A serious reproducible rules or observation flaw invalidates the checkpoint even if scores look good. |
| Reproducibility | Both adapter seeds, exact weights/versions, map and dataset manifests, training logs, and every evaluation trace are retained and independently replayable. |
| SFT-only gameplay gain | Against B-lite on the final test, win-equivalent score exceeds the unchanged base by at least 10 percentage points, and the lower 95% paired map-cluster confidence bound on the difference is above zero. Record the base's actual headroom before interpreting this result. |

These are proposed gates, not expected results. Report each seed and both decisions, including a usable warm start with no proven gameplay gain or a failed warm start. Prompt, teacher, simulator, or training changes after opening the final test require a new version and a fresh untouched test set before claiming a new final-test gain. A strong teacher score alone is insufficient; the learned model must meet its own readiness gates.

## Post-SFT test of the transfer hypothesis

Use a **small APEX-Agents subset** for the first exploratory baseline-versus-SFT comparison. The question is whether Polytopia-only SFT improves completion of unrelated professional work. This probe is separate from the Polytopia acceptance gates and does not select a training checkpoint. It replaces the previously proposed BBH, Game of 24, and GameBench panel for SFT-0.

Use the public [APEX-Agents 1.1 release](https://www.mercor.com/blog/introducing-apex-agents-1-1/), which provides professional tasks, files, tools, and an evaluation agent. Its domains include management consulting, investment banking, and corporate law. Our initial scope is consulting and investment banking, chosen for their relevance to analysis and multi-step decisions. This is a custom subset experiment, not a full APEX leaderboard result.

| Component | Proposed first-checkpoint protocol |
| --- | --- |
| Development pilot | Six separate tasks: three consulting and three investment banking. Run the unchanged 4B model to validate tool use, file access, grading, context requirements, and cost. Exclude these tasks and their shared company/world files from the scored subset. |
| Scored subset | 30 tasks: 15 consulting and 15 investment banking. Select with a recorded random seed from technically runnable tasks, spread across available worlds. After SFT, freeze exact IDs, exclusions and reasons, dataset revision, and file hashes before scored comparisons. Do not choose items based on SFT performance or cherry-pick baseline successes. |
| Models | The unchanged pinned Qwen3-4B-Instruct-2507 and the selected checkpoint from each of the two planned SFT seeds. Select checkpoints using Polytopia validation only. |
| Runs | One attempt per task per model: **90 scored task runs**, plus the six base-only development runs. No best-of-N selection or model-error restarts. |
| Main measure | Mean fraction of rubric criteria satisfied per task, using the pinned released grader. Average task scores equally and report both domains separately. This partial-credit diagnostic is our chosen measure, not an asserted official leaderboard metric. |
| Additional measures | Fully successful tasks under the released task-success rule; tool/format failures, timeouts, steps, generated tokens, elapsed time, and cost. |

Keep the agent scaffold, tool access, task instructions, decoding, context handling, and per-task token/tool-call/time limits identical across models. Preserve Qwen's normal chat interface; the Polytopia action-ID output format does not apply here. Per the user's sequencing decision, set up APEX only after SFT is complete. Run the six-task pilot using the unchanged base, then freeze numerical limits, task IDs, scaffold, and grader versions/settings before evaluating any SFT adapter on APEX. This is an exploratory evaluation specified after training, not a preregistered transfer study. Use the released rubric and grading behavior, including its treatment of conflicting answers. Keep task solutions and grading rubrics outside the acting model's context. Blind checkpoint identity during grading and save all traces and final artifacts.

The pilot checks whether this setup yields an interpretable signal at 4B. If the base cannot operate the tools, or every pilot task is at the floor or ceiling even on partial credit, report that limitation and resolve the harness or protocol before freezing it. Six tasks cannot establish the difficulty of the full subset. Do not adapt the scored subset or budgets after seeing SFT results. Neither development tasks nor scored tasks may enter later training or guide SFT checkpoint selection or hyperparameters. Do not set up or run APEX as a prerequisite for building the SFT pipeline.

For each SFT seed, report the paired score difference against the base, task-level wins/ties/losses, and an uncertainty interval clustered by shared world. With only 30 tasks and potentially few independent worlds, intervals will be noisy; one run per task also leaves execution variability unresolved. An improvement is an **early professional-task transfer signal**, not proof of general reasoning or strategy improvement. A flat result is inconclusive at this scale, especially if task-success rates are near zero. Public-data contamination and the absence of a matched non-game SFT control further limit causal interpretation. A larger controlled study follows only if warranted.

Budget this probe separately from game evaluation: **90 scored runs × measured mean cost per task**, plus the six-task pilot, sandbox overhead, and grading. Record model GPU time, tool costs, and judge API costs separately; task count alone does not establish a dollar estimate. No benchmark run has been executed or exact task manifest frozen by this document update.

SFT data should retain episode IDs, public observations, semantic actions, outcome, reward and terminal/truncation flags, model/teacher hashes, and sampling metadata. That makes later on-policy RL possible without deciding an RL objective now. At this checkpoint, rewards are used only to score games and diagnose labels. No return, advantage, critic, PPO ratio, or GRPO group is involved in the SFT gradient.

## Required checkpoint package and order of work

The final package contains a versioned experiment manifest; prompt-search candidates, development manifests, cost ledger, and frozen-prompt selection receipt; memory schema/builder revision, isolation/replay tests, and exact per-decision memory; simulator and native-rules receipts; split seeds and board hashes; teacher source/version, qualification and trace samples; training JSONL/Parquet with semantic actions and data audit; model/tokenizer/template revision hashes; package lock; two adapter weights and logs; base and SFT validation/test traces; confidence-interval calculations; cost ledger; frozen transfer-panel protocol and base/SFT results or an explicit unevaluated mark; and a one-page gate decision with each failure mode. Keep private omniscient simulator snapshots in a separate trusted archive, never in policy examples.

Execution order is: **complete and validate simulator → fix interface contract and reserve game/prompt-development splits → implement and validate factual memory → qualify teacher and freeze opponents → optimize and freeze starting prompt → collect/audit and render demonstrations → verify masking and fit sanity → run smoke → check saved positions and 100 pilot games → measure cost and decide whether to continue → optionally relabel public states → freeze main corpus → train two adapters → choose steps on game validation → run game final test → set up APEX and run the base-only development pilot → freeze and run the exploratory APEX subset → publish SFT-0 package**. This document ends at that decision. RL experiment design starts from its measured validity, game length, reward sparsity, throughput, and transfer baseline.

### Research basis

The staged teacher-then-RL idea is motivated by [Odysseus](https://arxiv.org/abs/2605.00347); other small-model game-training examples include [MARSHAL](https://arxiv.org/abs/2510.15414) and [SPIRAL](https://arxiv.org/abs/2506.24119). Their results do not establish that this simulator, this 4B checkpoint, or the proposed transfer panel will succeed. The model and training implementation details above rely on the official [Qwen model card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507), [TRL SFT documentation](https://huggingface.co/docs/trl/sft_trainer), and [PEFT LoRA documentation](https://huggingface.co/docs/peft/developer_guides/lora). Game-rule validation uses the pinned repository evidence and the independent native exceptions listed above.
