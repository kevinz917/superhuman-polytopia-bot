# Net-size sweep (Chinchilla-style) on Daytona: plan (2026-10-28, not started)

**Question.** For a 1v1 self-play run of a given budget, which network size gives the strongest bot? And how does
that best size move as the budget grows? We need this answer to size the next hero run. Today we pick the size by
feel. bn-main1 (10 h of 4x128 that lost to a 2x64) shows a wrong guess can waste a whole run.

**Method.** Train several net sizes from scratch with the same recipe. Score checkpoints by Elo against a fixed set
of anchor opponents, and plot Elo against compute for each size. The compute-optimal size at a budget is whichever
curve is on top there. Where the curves cross tells us how the best size moves with budget.

**Scope.** 1v1, 14x14, `proposed-v1` maps, real 2.17.3 rules, hero-1v1 recipe. 4p is out of scope until its Daytona
KL ~1 problem is solved (see docs/hero-daytona-2026-10-28.md).

**Cost.** Core plan ~$700, about 9 h of wall clock per arm, with the arms run in parallel. Optional add-ons ~$540.
Details are under "Budget".

---

## 1. Background: the principles we use

1. **Error has three parts.** A ceiling no bot can pass, a capacity penalty (the net is too small), and an
   undertraining penalty (too few samples). More data fixes only the last; a bigger net fixes only the middle.
2. **Cost ≈ size × samples.** With a fixed budget, a bigger net gets fewer samples. For us a bigger net costs more
   twice over: actors run it to play, and the learner trains it.
3. **At a fixed budget there is a best size.** Too small hits its capacity ceiling. Too big is still undertrained
   when the money runs out.
4. **The best size moves predictably with budget.** That lets cheap sweeps decide the size of an expensive run.
5. **The schedule must match the run length.** You can't read budget-X performance off a mid-run checkpoint of a run
   whose LR decay was planned for a later end. This sweep runs at constant LR so that every checkpoint is fair. An
   optional add-on checks that LR-decay tails don't reorder the sizes (section 7, add-on D).
6. **Compute-optimal is not deployment-optimal.** We serve with search, and the browser bot runs the net in WASM.
   When two sizes are within noise, the smaller one is the better product.

Two things differ from Chinchilla's setting:
- **Our data is generated by self-play**, not read from a fixed pile.
- **Our metric is Elo against fixed anchors**, not held-out loss. Elo is non-transitive and noisy, so anchors come
  from several lineages and every point gets hundreds of games.

## 2. What already exists (free data)

## 3. Arms (net sizes)

Width and depth scale together, as in the existing 2x64 → 4x128 step. Most compute goes to the trunk: 3×3 convs on
all 196 tiles. Trunk multiply-adds per forward ≈ 196 × blocks × 18 × width².

| arm | blocks × width | params (approx.) | trunk MACs / forward | × 4x128 | role |
|---|---|---|---|---|---|
| S | 2x64 | ~0.55 M | 29 M | 0.13 | small side of the U (add-on A) |
| **H** | 4x128 | 1.97 M | 231 M | 1 | **reused from hero-1v1**, plus short replica R |
| **L** | 6x192 | ~5.2 M | 780 M | 3.4 | **core** |
| **XL** | 8x256 | ~11 M | 1.85 G | 8.0 | **core**, may be swapped (see the calibration gate) |

**Why the core goes up, not down.** Calibration should confirm this, but on the Daytona stack small nets are
unlikely to be cheaper per sample. The 1v1 actors are CPU-bound on engine and encode work, since the net is served by
the GPU inference server. The 4x PRO 6000 learner is bound by batch assembly (~125k samples/s live against 206k
train-only). Neither wall depends much on net size below 4x128.

So at equal dollars, 2x64 gets about the same number of samples as 4x128 and can win only if it learns faster per
sample. The decision we need is "should the next hero run be bigger than 4x128?", and only the bigger arms answer it.

## 4. Phases

### Phase 0: calibration (~$40, ~2 h)

This phase measures what each size costs per sample on Daytona. That gives the compute axis in dollars and the right
number of actors per arm.

1. **Learner bench.** Run `node.py learner` on one healthy 4x PRO 6000 box with specs for 2x64, 4x128, 6x192 and
   8x256: hero config, batch 262,144, minibatch 16,384, 1 epoch, bf16 trunk. Record train-only samples/s and peak
   GPU memory. If 8x256 runs out of memory, use `grad_accum` 2 and keep the minibatch at 16,384. Changing the
   minibatch was the bn-main1 confound and is not allowed.
2. **Smoke per size.** Run a 25-minute `node.py smoke` per size (learner plus 1–2 actor boxes). Record the live
   learner samples/s (assembly included), the actor box rate with the bf16 server, the KL, and the actor/learner
   logp agreement.
3. **Write `runs/sweep/calibration.json`** with, per size:
   - learner cap and actor box rate;
   - actor count = ceil(learner cap / actor rate);
   - $/h for that layout (`cost_matrix.py` prices);
   - **$/B = $/h ÷ (samples/s × 3600 / 1e9)**.

**Calibration gate:**
- If an arm's $/B means the core budget buys fewer than **1.0 B samples**, replace it with the next size down
  (8x256 → 5x160). Below 1 B samples even 4x128 could not beat c3 reliably, so such an arm would yield a flat curve
  and no information.
- If 2x64's $/B comes in at least 1.8x cheaper than 4x128 (that is, the walls do depend on size), promote add-on A
  into the core. The small side of the U then becomes informative.

**Expected values (to be replaced by calibration):**
- **4x128:** ~$74/B. The Daytona layout from the hero runs is 4x PRO 6000 learner + 5 PRO 6000 actors at
  ~$30/h, ~112k/s after reclaims.
- **6x192:** learner-bound at ~55–60k/s, so it needs 2 actors at ~$19/h, ~$95/B.
- **8x256:** ~25k/s, 1 actor at ~$15/h, ~$170/B.

The bigger nets cost less per hour, because they need fewer actors, but more per sample.

### Phase 1: the core sweep (~$560 GPU + ~$100 eval)

**Arms L and XL**, launched in parallel:
- Each trains from random init until it reaches **budget B ≈ $210** of compute (B is defined in section 5).
- Expected wall clock: L ~11 h at ~$19/h; XL ~14 h at ~$15/h. More actors would not speed XL up, since its learner is
  the limit.
- The recipe is identical to hero-1v1 except for three changes:
  - `learning_rate_end` = `learning_rate` = 3e-4 (constant LR);
  - `checkpoint_every` 20 (spot);
  - `snapshot_every` 100 (denser curve points, 26 M samples each).
- Same seed 801, same map seed range, same opponent mix (self-play 0.5, historical 0.1, pool), same omniscient
  critic.

**Arm R (replica):** 4x128 on Daytona with seed 803, run to **$70** only (~2.3 h). R's curve must sit inside the
noise band of hero-1v1's re-scored curve at the shared grid points ($10–$70). If it doesn't, the hero curve doesn't
transfer: extend R to the full B before drawing conclusions (add-on B).

**Stopping.** Stop on a target **sample count** computed from calibration: samples = B ÷ ($/B). This keeps reclaim
downtime out of the compute axis. Also set `--max-usd` to 1.4 × B as a safety cap on real spend.

### Phase 2: evaluation (rolling during training, ~$100)

**Anchor ladder.** Seven fixed opponents, all playable under the real rules, spanning roughly 800 Elo:

| anchor | what it is | why |
|---|---|---|
| A0 | hero-1v1 update-500 | weak, so the early points of every arm have something to beat |
| A1 | hero-1v1 update-1500 | weak/medium |
| A2 | c3 (`c3-maps-ctl-update-4854`) | medium, other lineage (2x64, OMNI recipe) |
| A3 | champion (`scratch-cont-2-final`) | strong, 2x64 |
| A4 | bn4 (`bn-main4/final`) | strong |
| A5 | hero-1v1 final (u14871) | stronger, 4x128 |
| A6 | hero-1v1-cont1h final (u11650 of cont) | strongest 1v1 bot |

The anchors play a round robin once: 21 pairs × 128 games. A Bradley-Terry fit gives each anchor a fixed rating,
with A3 (champion) pinned to 0.

**Candidates.** For each arm, take the snapshot nearest each point of the dollar grid **$10, 15, 22, 33, 50, 75, 110,
160, 210** (×1.5 steps; 9 points per arm). The hero curve is converted to dollars as samples × 4x128 $/B.

**Games.** Each candidate plays every anchor on **64 maps × 2 seats** (896 games). All candidates use the **same map
seeds (base 540000)**, so comparisons between arms are paired. The three points around each crossover get a second
64 maps. Raw policy, no search. Same arena code as the hero ladder (`hero_arena` jobs on 4-vCPU CPU boxes, 8 maps
per box).

**Noise.** At ~50%, 128 games give ±31 Elo of standard error against a single anchor. Pooled over the informative
anchors, a candidate's rating is good to about ±15–20 Elo standard error. Paired differences between arms at the
same grid point are tighter still. That locates a crossover to within about a ×1.5 grid step of dollars.

**Volume.** 3 full curves × 9 points plus R's 6 points, at 896 games each ≈ 30k games, plus 2.7k for the anchor
round robin and ~3k for crossover refills: ~35k in all.

### Phase 3: analysis (no GPU cost)

`experiments/sweep/analyze.py` writes `docs/chinchilla-sweep-result-<date>.md`:
1. **Ratings.** Bradley-Terry Elo for every candidate against the fixed anchors. 95% intervals from a bootstrap
   over maps (seat pairs kept together, as in the B1 analysis).
2. **Curves.** Elo against compute for every arm, drawn three ways:
   - Daytona dollars (the decision axis);
   - training FLOPs ≈ trunk MACs × samples × (1 actor forward + 3 for learner forward/backward + 1 value pass),
     which is hardware-free and comparable to other scaling work;
   - samples.
3. **Frontier and crossovers.** The best arm at each grid point. Each crossover's budget is estimated by
   interpolation in log dollars, with a bootstrap interval.
4. **Fits.** Per arm, Elo(D) = E∞ − A·D^(−β), with D in samples. E∞ is that size's capacity ceiling. From the fits:
   - the compute-optimal size curve N_opt(C);
   - with ≥2 crossovers, the exponent a in N_opt ∝ C^a, reported with its interval and labeled as a 3–4-point
     estimate.
5. **Decision.** Extrapolate to the next hero run's budget (the last two were ~$600–1,100) and give:
   - the recommended size;
   - the predicted Elo of that size against 4x128 at that budget, with its interval;
   - how far the extrapolation reaches beyond the measured range. $210 → $800 is ×3.8; anything beyond about ×5
     gets flagged.

## 5. Definitions that keep the comparison fair

- **Compute.** Calibrated steady-state Daytona dollars: samples × $/B(size, best layout). For each size, $/B uses
  its cheapest healthy layout from Phase 0: 2x vs 4x PRO 6000 learner, and actor count. Real spend, including
  reclaims, is reported separately.
- **Budget B.** min($210, the hero curve's constant-LR range in dollars = 2.75 B × 4x128 $/B). At ~$74/B the
  second term is ~$204, so B is about $205–210.
- **Held constant across arms:** batch 262,144, minibatch 16,384, 1 epoch, LR 3e-4 (constant), entropy .01,
  γ .995 / λ .99, turn clock γ .99 / λ .95, advantage floor .05, omniscient critic (scaled with the net), opponent
  mix, map distribution, `max_lag` 10, bf16 trunk on the learner and the server.
- **What varies:** blocks × width only, plus the actor count, which changes throughput but not the recipe.

**Optional add-ons:**
- **A. 2x64 arm to B (+$230):** the small side of the U and a cleaner FLOPs-axis law. It moves into the core
  automatically if calibration shows 2x64 is at least 1.8x cheaper per sample.
- **B. Full 4x128 replica to B (+$150 more):** a second seed at every grid point. Needed if R disagrees with the
  hero curve; otherwise it measures seed noise.
- **C. LR probe for the biggest arm (+$30):** 45 minutes at 1.5e-4 against 3e-4. This checks that the shared LR
  isn't handicapping the bigger net.
- **D. Decay tails (+$100):** from each arm's final checkpoint, decay the LR 3e-4 → 1e-4 over 15% more compute, then
  re-score. If the tails reorder the arms, principle 5 bites and the decision should use the tail points.

Everything together comes to ~$1,200. For comparison, one 12-h hero run on Modal is ~$800. A full hero-1v1 lineage
cost ~$1,100.

## 8. Risks and what we do about them

| risk | effect | mitigation |
|---|---|---|
| One seed per arm | a lucky or unlucky seed moves a crossover | arm R / add-on B give a seed-noise estimate; calls within ~30 Elo count as ties |
| Shared LR suits 4x128, not bigger nets | XL looks worse than it is | watch KL and clip fraction in the first hour; add-on C |
| Hero curve came from Modal hardware | systematic offset at H | replica R; extend it if R lands outside the band |
| Elo non-transitivity | a style that beats the 4x128 anchors inflates a rating | anchors from three lineages (hero, scratch/champion, c3); report the per-anchor table too |
| Big-net actors slower to serve | rate below plan | calibration measures server rate; add an actor box if needed |
| 8x256 learner out of memory | arm can't run as specified | `grad_accum` 2 at the same minibatch |
| Daytona spot reclaims, bad hosts, learner hangs | lost time, not lost compute (axis is samples × $/B) | existing keeper: 20-update checkpoints, gpu_check, stall/KL recycling |
| Capacity: 3 arms need ~14–16 PRO 6000 GPUs at once | arms can't start together | stagger the arms; compute is measured per arm, so staggering doesn't bias anything |
| Extrapolating ×4 past the measured range | wrong size for a long run | report the extrapolation ratio; if it's above ×5, run one more arm at a larger B before committing a hero run |

## 9. What we get

1. A frontier showing which size wins at each budget from $10 to ~$210, and the crossover budgets with intervals.
2. A recommended size for the next hero run, with its predicted gain over 4x128.
3. A per-sample cost table by size on Daytona, which is also useful for any future run.
4. A FLOPs-axis curve set that can be compared with published game-RL scaling work.
5. A reusable sweep harness (`sweep.py`, `analyze.py`), so the sweep can be rerun cheaply after a big recipe change.
