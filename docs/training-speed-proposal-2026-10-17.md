# Proposal: faster Polytopia training feedback

The largest immediate improvement is to evaluate early checkpoints and report each diagnostic as soon as it completes. The largest recurring compute opportunity is the inference path. Increasing the training microbatch again is unlikely to produce a large improvement by itself.

This analysis covers the latest completed `efficient-smoke-v1` 10k SFT run and its bounded evaluation, using local receipts and current source inspected on October 17, 2026. It does not launch training or change the frozen research protocol. The checkpoint learned saved-position imitation, but did not pass the gameplay diagnostic; there is no accepted main checkpoint.

| Measured stage | Elapsed time | Interpretation |
|---|---:|---|
| Fresh 128-example fit invocation | 16.85 min | Correctness check before the smoke run |
| 10k training invocation | 65.05 min | Optimizer itself took 62.15 min on one B200 |
| 5k saved-position evaluation | 15.54 min | Ran concurrently with games |
| 50-game bounded evaluation | 76.04 min | Four A100 workers; one game still incomplete |
| Training invocation to position-summary generation | 141.31 min | Position results were already available after 80.81 min |
| Extra wait before position-summary generation | **60.50 min** | Driver waited for games before summarizing positions |

The fit-to-summary interval was 158.29 minutes. These are elapsed intervals, not sums of concurrent worker time. They exclude earlier development, data repair and failed benchmark attempts. The driver may have exposed raw progress earlier; the measured reporting delay refers specifically to summary generation.

Evidence: [training driver](../runs/sft0/efficient-training-driver-status-v4.json), [checkpoint driver](../runs/sft0/efficient-checkpoint-status-v3.json), [training summary](../runs/sft0/efficient-smoke-result-v1/summary.json).

Previous efficiency work already delivered CPU/inference overlap (1.50x on a controlled prefix pilot), microbatch 4, response-only vocabulary projection, and length sorting within effective batches. Full training improved only from 65.23 to 62.15 optimizer minutes: 1.050x. Microbatch 8 and 16 were slower than 4 in the existing benchmark. Six benchmark versions and repair/recovery stages contributed one-time delay; those should not be treated as inevitable per-experiment costs. See [implementation evidence](sft-efficiency-implementation.md).

The latest game run made 15,953 model calls, averaging 319 per allocated game, and processed 64.52 million prompt tokens for 145,796 output tokens. Mean prompt length was 4,044 tokens. The model-call path occupied 95.5% of summed worker time, including tokenization and decoding; this is not GPU utilization or a measured prefill/decode split. Perfectly removing the remaining 4.5% could improve that aggregate measure by only about 1.047x. The counterfactual does not model critical-path imbalance or CPU work inside the model-call path.

The inference server still processes one lane's whole batch at a time with `transformers.generate`; it does not merge pending requests across lanes. Mean actual batch size was 4.55. Shards are fixed, so work cannot migrate when one finishes. The slowest worker occupied 75.2 minutes versus 41.7–52.9 minutes for the other three. A global ready queue can reduce imbalance and improve batching, though one game's actions remain sequential and more concurrency alone does not guarantee a proportional gain.

Evidence: [runtime receipt](../runs/sft0/efficient-game-runtime-v1.json), [coordinator](../runs/sft0/efficient-games-v1/coordinator.json), [queue implementation](../src/polytopia_bot/learning/efficient_gameplay.py), [generation implementation](../src/polytopia_bot/learning/serving.py).

I also ran a new CPU-only token experiment on every twentieth example of the existing 10k training set, using its saved tokenizer. This is a deterministic 500-example diagnostic, not a statistical estimate with confidence bounds.

| Component | Mean tokens in sampled inputs |
|---|---:|
| Public board/entities/state | 1,769 |
| Legal-action catalog | 1,067 |
| System instructions | 546 |
| Rule definitions | 405 |

Components are tokenized independently, so they do not sum exactly to the full prompt. The existing format is already compact. Grouping legal actions by kind/source/parameter and encoding repeated terrain values as runs reduced total input from **4,007 to 3,338 tokens, or 16.7%**, including additional decoding instructions. All 500 observations and catalogs reconstructed exactly. Maximum sampled input fell from 14,773 to 9,369 tokens. This proves lossless transport recovery, not that the model can use the encoding equally well. Some terrain arrays grow under run-length encoding; a production candidate should choose the shorter representation. Grouped action indices may also make action selection harder.

The experiment is reproducible with `training/.venv/bin/python runs/speed-audit-2026-10-17/analyze.py`. [Script](../runs/speed-audit-2026-10-17/analyze.py), [results](../runs/speed-audit-2026-10-17/token-audit.json). No GPU speedup was measured. This result does not support claiming that a serialization change alone will deliver 3–10x acceleration.

1. **Expose useful feedback within 10–20 minutes of a warm run.** Save adapters every approximately 1,000 examples and evaluate a fixed 512-position development diagnostic asynchronously. At the current average rate, 1,000 examples take about 6.2 optimizer minutes; startup, checkpoint transfer and evaluation add overhead. Immediately publish aggregate and action-family results, then add a small, predeclared paired gameplay diagnostic. Current checkpoints at steps 40, 79 and 157 are only saved, not evaluated during training. Remove the dependency between position-summary reporting and game completion. Reuse immutable data, tokenizer and qualification receipts when their content hashes match; requalify changed runtime components. Engineering estimate: half a day to one day. The 10–20 minute target is early diagnostic feedback, not proof of stronger gameplay or a replacement for full evaluation.

2. **Replace the lane-sized inference calls with a persistent serving engine and a shared request queue.** Benchmark vLLM with the unchanged base model, frozen adapter, tokenizer and prompt first. Feed it independent pending game decisions, using token-budget batching and bounded concurrency rather than fixed lane batches. Start with concurrency 8/16/32 per GPU and tune against memory, latency and completed decisions per second. Keep environment ownership in CPU workers and route responses by game and observation revision. Preserve cloud-owned coordination; add per-game resumable snapshots and durable completion records. Development target: 2–4x inference-path throughput, explicitly unmeasured. Engineering estimate: two to four days including validation. If the model-call path becomes 2x or 4x faster with all else held fixed, Amdahl's law gives about 1.91x or 3.52x aggregate worker-time improvement; end-to-end elapsed speedup must be measured separately.

   vLLM documents continuous batching, prefix caching and LoRA support in its [official overview](https://docs.vllm.ai/en/latest/). Check exact pinned-version/model compatibility and compare outputs on a fixed training-split prompt replay before accepting the backend. Numerical and batching differences can change greedy actions; rerun paired base/adapter evaluation under the common new backend rather than assume bitwise equivalence.

3. **Benchmark padding-free training and reduced activation recomputation.** Keep the effective batch of 64, response-only objective, and original example membership per optimizer update. Use variable-length attention with explicit sequence boundaries, so examples cannot attend to one another. Preserve response-token normalization and positional resets. Benchmark full versus selective versus disabled gradient checkpointing, subject to longest-batch memory tests; current 35.88 GB peak allocation does not prove every configuration fits. Instrument actual attention kernels, forward/backward time, padding work, host stalls and device utilization. SDPA already may use fused attention, so merely changing an attention flag is not a demonstrated gain. Target 1.5–2x training throughput only if the matched benchmark supports it. Engineering estimate: one to three days. See Hugging Face's [padding-free training documentation](https://huggingface.co/docs/transformers/main/padding_free); it describes current APIs, whereas this repository pins Transformers 4.57.1. Treat integration as a versioned runtime change.

4. **Test a compact, cache-friendly observation format as a separate learning experiment.** Start with the measured 16.7% token reduction, exact roundtrip checks across the full corpus, and a small fit/behavior comparison before changing the default. Put stable instructions and definitions before changing state, with the legal catalog at the end. Currently sorted JSON places `legal_actions` near the beginning, limiting reusable prefix length. The 546-token system instruction is about 14% of sampled input; caching only that prefix cannot remove most prefill work. Do not reuse KV state after changing adapter weights, or assume that identical suffixes remain reusable after an earlier field changes. vLLM's [prefix-caching documentation](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/) confirms that reuse requires a shared prefix and accelerates prefill, not decoding. Engineering estimate: one to two days plus a bounded learning comparison. Do not multiply token savings, cache savings and packing gains as though they were independent.

5. **Improve the rate of learning useful behavior.** The latest checkpoint reached 59.20% teacher agreement versus 14.94% for the base, with 100% first-attempt validity. However, movement exact agreement was only 13/575, and only 14/50 games reached native outcomes (7 wins, 7 losses). Thirty-five hit the research horizon and one hit the time budget. Exact agreement understates performance when teacher actions tie, so use tie-aware movement scoring plus closed-loop expansion/capture/completion measurements. Existing repaired data already balances phase/action families, caps end-turn examples, and includes model-collected teacher relabels: simply proposing class balancing again misses the remaining problem. Test public-state spatial features, tie-aware legal-action targets, and iterative training-split relabeling of policy-visited states. Keep validation traces diagnostic and avoid collecting training labels from evaluation maps. This is a hypothesis-driven data/interface experiment, not a promised speed multiplier.

If learning a general-purpose LLM policy remains the research objective, compare a 1–2B student on the same task as an additional cheap development baseline; do not assume it will match the 4B model. If the objective is primarily a strong, fast game bot, the more substantial architectural option is a compact policy network over typed board/unit/action tensors with a legal-action scoring head. That avoids rendering and rereading thousands of text tokens for every move, but changes the research question and requires separate evidence of learning quality. Merely replacing nine output tokens with a one-pass head would leave the expensive input processing in place.

Recommended execution order: early reporting and profiling first; serving backend second; training kernel/checkpointing benchmark third; observation and learning experiments after the controlled baselines exist. Keep the next engineering pilot bounded to a fixed prompt replay and representative training batches rather than repeat a full 10k fit for each implementation attempt. Measure cold and warm time, GPU-seconds and cost separately. Reuse the same hardware for comparisons; a faster GPU is not an independent explanation when data and contexts also changed.

The practical targets are **10–20 minutes to an early learning diagnostic**, and, if the serving/training benchmarks pass, roughly **55–85 minutes for a full warm smoke iteration** instead of the observed 141-minute training-to-summary path. The latter assumes about 31–41 minutes of training, roughly 19–38 minutes for games after acceleration, concurrent saved-position evaluation, and additional overhead; it is a planning target rather than a prediction. A 5–10x reduction in feedback delay is plausible through earlier evaluation, but a 5–10x reduction in identical full-run computation is not established by current evidence.

Promote a candidate only after representative fixed-work throughput measurements, response-loss/gradient checks for trainer changes, longest-input stress, adapter reload verification, and paired gameplay under the unchanged completion criteria. The small development diagnostic is for iteration; keep the full 5k-position/50-game checks and final-test separation. Report time-to-first-signal separately from time-to-qualified-gameplay. Faster detection of a failing policy is still useful, but it must not be reported as successful learning.
